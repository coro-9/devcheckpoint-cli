# دليل DevCheckpoint بالعربية

أداة محلية صغيرة لحماية العمل قبل تطبيق ملفات patch على مستودع Git. تحفظ الملفات المتتبعة والمعدلة وغير المتتبعة والمتجاهلة، ثم تجرب التغييرات في نسخة مؤقتة وتتحقق من البصمات قبل السماح بالتطبيق الفعلي.

لا تحتاج إلى حساب OpenAI أو مفتاح API أو Codex. ويمكن لأي مساعد برمجي تشغيلها من الطرفية وفق صلاحيات المستخدم.

## بداية سريعة على Windows دون تثبيت

تحتاج إلى Node.js 24 أو أحدث وGit. وعلى Windows تحتاج أيضاً إلى Windows PowerShell وicacls. لا توجد تبعيات npm وقت التشغيل.

فك ZIP المراجع وافتح PowerShell في مجلد الأداة:

```powershell
node bin/devcheckpoint.mjs --version
node bin/devcheckpoint.mjs --help
node bin/devcheckpoint.mjs doctor
npm run example
```

ينشئ المثال مستودعاً اصطناعياً جديداً في المجلد المؤقت ويجرب التخطيط والنسخ والتجربة والتطبيق والاستعادة وفشل التحقق مع الاسترجاع. لا يستخدم مشروعك الحقيقي. لا حاجة إلى تثبيت عام أو حزمة من السجل. لتطوير الأداة استخدم `npm test` و`npm run check`.

يفحص `doctor` إصدارات الأدوات وتوفرها للقراءة فقط. أضف `--repo "C:\Projects\example-app"` لفحص بنية Git الأساسية دون تجزئة كل المحتوى. تبقى فحوص الروابط والتدفقات والبصمات الكاملة للتخطيط والتجربة. لا ينشئ `doctor` نسخة ولا يشغل اختبارات المشروع. تفرض العمليات شرط Node.js 24 أو أحدث.

## التسلسل الآمن

1. أوقف عمليات البناء والمراقبة وأي برنامج يكتب إلى المستودع.
2. نفّذ `plan` لفحص المستودع وترتيب ملفات patch وعرض أوامر التحقق. لا يغيّر المستودع الأصلي.
3. نفّذ `backup` مع مجلد جديد خارج المستودع. النسخة تحتوي على الملفات المتجاهلة أيضاً، وقد تحتوي على أسرار؛ لا تنشرها.
4. راجع أوامر التحقق ثم وافق صراحة باستخدام `--approve-commands` لتشغيل `rehearse`.
5. بعد نجاح التجربة وموافقة صاحب المشروع، نفّذ `apply --confirm --approve-commands`.
6. للتراجع عن هذه العملية استخدم `restore --confirm`. إذا ظهرت تعديلات أحدث، تتوقف الأداة ولا تمحوها تلقائياً.

احصل على patch مبني على **حالة الهدف الحالية قبل التغيير** دون تعديل الهدف نفسه. إذا كان الهدف نظيفاً عند commit اسمه الرمزي `BASE`، طوّر التغيير في clone عادي منفصل واحفظه في commit `PROPOSED`، ثم صدّر منه:

```powershell
git diff --binary --output=C:/Changes/change.patch BASE PROPOSED
```

استبدل الاسمين بمعرّفات commits الحقيقية. لا تطبق الملف مجدداً على نسخة التطوير المعدلة. إن احتوى الهدف على عمل غير ملتزم، يجب أن يعتمد patch على تلك البايتات الحالية؛ لا تمح العمل أو تعِد ضبطه لمجرد جعل patch ينجح. يفحص `plan` قابلية التطبيق.

```sh
node bin/devcheckpoint.mjs plan --repo "C:\Projects\example-app" --patch "C:\Changes\change.patch"
node bin/devcheckpoint.mjs backup --repo "C:\Projects\example-app" --backup-dir "C:\Recovery\before-change"
node bin/devcheckpoint.mjs rehearse --repo "C:\Projects\example-app" --backup-dir "C:\Recovery\before-change" --patch "C:\Changes\change.patch"
node bin/devcheckpoint.mjs status --backup-dir "C:\Recovery\before-change"
node bin/devcheckpoint.mjs apply --repo "C:\Projects\example-app" --backup-dir "C:\Recovery\before-change" --confirm
node bin/devcheckpoint.mjs status --backup-dir "C:\Recovery\before-change" --verify --repo "C:\Projects\example-app"
node bin/devcheckpoint.mjs restore --repo "C:\Projects\example-app" --backup-dir "C:\Recovery\before-change" --confirm
```

المثال أعلاه يفحص التغييرات فقط؛ لا يدّعي تنفيذ اختبارات للمشروع. أضف ملف إعدادات `--config` في التخطيط والتجربة لتشغيل اختبارات فعلية. راجع مثال `examples/checks.json`.

يوفر [README الإنجليزي](../README.md#one-complete-workflow) تسلسلاً كاملاً بالإعدادات وموافقة الأوامر المستقلة `--approve-commands` ثم موافقة التطبيق `--confirm`. الأوامر مصفوفات argv دون shell. اسم الأمر نص فريد يحتوي حروفاً أو أرقاماً أو `_` أو `-`. إن حذفت `timeoutMs` فالافتراضي 120000 مللي ثانية؛ إن قدمته يجب أن يكون عدداً صحيحاً من 1 إلى 3600000. يُرفض الصفر وnull والقيم المنطقية والنصوص والكسور والقيم خارج النطاق قبل التنفيذ.

## فحص الحالة دون تغييرها

```powershell
node bin/devcheckpoint.mjs status --backup-dir "C:\Recovery\before-change"
node bin/devcheckpoint.mjs status --backup-dir "C:\Recovery\before-change" --verify
node bin/devcheckpoint.mjs status --backup-dir "C:\Recovery\before-change" --verify --repo "C:\Projects\example-app"
```

الوضع الافتراضي يراجع بيانات الأدلة المسجلة وملفات سلامتها فقط؛ لا يعيد تجزئة كل محتويات النسخة ولا يفحص المشروع الحالي ولا يمنح إذناً بالاستعادة. `--verify` يعيد التحقق الكامل من النسخة. ولا يفحص الهدف الحي إلا مع `--verify --repo`. الحالة المنقطعة أو غير المكتملة لا تتحول إلى نجاح لمجرد أن البيانات قابلة للقراءة. لا يصلح `status` الملفات ولا يحذف قفلاً ولا يشغل أوامر.

رموز الخروج الثابتة: `0` نجاح، `1` خطأ غير متوقع، `2` استخدام/إعدادات، `3` موافقة مفقودة، `4` حالة غير مدعومة، `5` اختلاف/سلامة، `6` Git/عملية، `7` فشل تحقق وقد تمت الاستعادة، `8` حاجة إلى معالجة الاسترجاع، `9` قفل، `10` مساحة غير كافية أو تعذر فحصها. راجع حقل الاسترجاع؛ الخروج غير الصفري ليس نجاح تطبيق.

## معالجة المشكلات

- عند فقد أداة أو مسار: ابدأ بـ`doctor` وصحح المتطلب أو المسار بنفسك؛ لا يحدث تثبيت تلقائي.
- المستودعات المرتبطة أو submodules أو النسخ shallow/partial غير مدعومة؛ استخدم مستودعاً مستقلاً مدعوماً دون تجاوز الحواجز.
- إذا كتب validator داخل المشروع فحوّل مخرجاته إلى مكان خارجي. أوقف العمليات الكاتبة ولا تبدأ استعادة حين تكون حياتها غير مؤكدة.
- عند قفل قديم، تحقق من العملية أولاً. لا تحذف قفلاً مجهولاً. تدعم الاستعادة المقصودة `--recover-lock` فقط بعد زوال PID وتوقف الكتابة.
- عند اختلاف أو استعادة منقطعة، احفظ العمل الجديد والأدلة وعالج التعارض؛ لا تفرض الاستبدال أو تعدّل manifest لتمرير الفحص.
- عند رمز 10 وفّر مساحة كافية؛ التقدير لا يحجزها ولا يبرر حذف نسخ الاسترجاع.

## حدود مهمة

- نسخة التجربة ليست بيئة أمنية معزولة. الأوامر تعمل بصلاحياتك وقد تستخدم الشبكة، لذلك تتطلب موافقة صريحة.
- يجب ألا تغيّر أوامر التحقق ملفات المستودع. اجعل مخرجات البناء خارج المستودع.
- يدعم الإصدار الأول مستودعات Git العادية ذات مجلد `.git` مستقل والتغييرات على الملفات العادية. لا يدعم submodules أو linked worktrees أو أنواع الملفات الخاصة.
- يسجل الروابط دون تتبع أهدافها، لكنه يرفض التجربة والتطبيق عندما يحتوي المستودع على روابط.
- يُرفض أي اختلاف غير معروف أو اختبار ناقص أو ملف دليل مفقود. لا تكفي نتيجة خروج صفر لإثبات أن الاختبارات نُفذت.
- قد يتطلب انقطاع الاستعادة أو وجود كتابة جزئية معالجة يدوية باستخدام النسخة المحفوظة. لا يوجد خيار لإجبار الاستبدال.
- في الإصدار 0.1.1 يفحص `plan` ملف patch واحداً دون نسخ المستودع. لا يثبت ذلك بصمات النتائج أو نجاح الاختبارات؛ تبقى التجربة الكاملة مطلوبة. تستخدم سلسلة patches نسخة مؤقتة واحدة. تُحذف نسخة التجربة الناجحة فقط بعد التحقق من استعادتها، مع إبقاء النسخة الاحتياطية والأدلة.
- تفحص الأداة المساحة المتاحة قبل النسخ والتطبيق والاستعادة. التقدير لا يحجز المساحة فعلياً؛ وقد تتطلب أخطاء امتلاء القرص اللاحقة معالجة يدوية. رمز الخروج 10 يدل على عدم كفاية المساحة أو تعذر التحقق منها.
- نتائج التوافق الفعلية موجودة في `docs/verification.md`. لا ندّعي اختبار Linux أو macOS في هذه النسخة.

يتضمن الإصدار 0.1.2 سير CI على Windows وNode 24 باستخدام إجراءات رسمية مثبتة ببصمات commits كاملة، دون تبعيات أو نشر. يفحص مستودعات اصطناعية وZIP المستخرج. لم يُنفذ هذا السير على GitHub بعد؛ التحقق المحلي ليس دليلاً على نجاح CI مستضاف. راجع [تعليمات Codex الاختيارية](codex.md): يمكنك دمجها يدوياً في `AGENTS.md`، ولا تعدل الأداة تعليماتك تلقائياً ولا تعتبر النجاح موافقة.

راجع README.md وSECURITY.md وLIMITATIONS.md قبل الاستخدام على مشروع حقيقي. لا تنشر النسخ الاحتياطية أو السجلات الخاصة.
